# Key Management

**Last reviewed: Sprint 32 (2026-06)**

## Key hierarchy

Every WeVibe org has one root secret: the **org master key** (`K_master`). All other
keys derive from it.

```
K_master  (32-byte random secret, leader-generated at org creation)
    │
    └── per epoch e, via HKDF-SHA256(K_master, "epoch-{e}-{purpose}")
            ├── K_enc(e)   — content encryption key
            └── K_audit(e) — audit log encryption key
```

Keyword terms and weights are stored in plaintext on-chain as discovery labels (`KeywordWeight.Keyword` + weight). This is an accepted tradeoff in the current architecture.

A separate **moderation keypair** is generated at org creation:
- `PK_mod(e)` — X25519 public key. Broadcast on-chain in org config so contributors can encrypt DEKs to it.
- `SK_mod(e)` — X25519 private key. Never leaves moderator custody. Distributed via sealed envelopes managed by the leader.

`PK_mod`/`SK_mod` is used only to decrypt pending submissions for moderator review. It does not co-sign chain actions. On-chain signing authority remains the leader only (DECISIONS `D-LEADER-SOLE-SIGNER`).

## Who holds what

| Key | Who holds it | Where stored |
|---|---|---|
| `K_master` | Org leader | OS keychain (`org-{id}-master`) |
| `SK_mod(e)` | Leader + invited moderators | OS keychain (`org-{id}-mod-privkey`) |
| `K_enc(e)`, `K_audit(e)` | All members (derived or unsealed) | In-memory after membership sync |
| Recovery phrase | Org leader | Offline (paper, password manager) |
| Identity keypair | Every agent | OS keychain |

Sealed envelopes are distributed peer-to-peer (CLI, dashboard download, secure file drop). wevibe-chain stores only the metadata needed to validate rotations; it never holds the encrypted envelopes themselves.

## Sealed envelopes

When a member is invited, the leader seals epoch keys to the invitee's X25519 public key
using ECDH + AES-256-GCM. The sealed blob is delivered out-of-band (for example via CLI,
dashboard download, or secure file transfer).

Leaders should keep a personal envelope sealed to their identity key so they can recover
`SK_mod` if the local keychain entry is lost. Anchor tooling (`anchor invite`, `anchor rotate`)
automates envelope generation and storage under `~/.wevibe/identity/`.

## Recovery phrase

At org creation, `wevibe_create_org` displays a **24-word BIP39 recovery phrase** that
encodes `K_master`. This phrase is the only way to reconstruct `K_master` if the
local keychain entry is lost.

**The phrase is shown once. If you do not record it, it cannot be retrieved later.**

The phrase encodes raw key material. Treat it with the same security as a private key:
- Store it offline (paper, hardware vault, password manager with strong master password)
- Never store it in plaintext on the same device as the running agent
- Never paste it into any agent, AI tool, or chat interface

To recover `K_master` from the phrase:

```
> Call wevibe_recover_org with your recovery phrase.
```

This reconstructs `K_master` and re-derives all epoch keys into local memory. Existing
sealed envelopes remain valid; regenerate and redistribute them if devices were lost.

## Key rotation

Epoch rotation (`wevibe_rotate_epoch` — not yet implemented in MCP tooling) generates new
`K_enc(e+1)`, `K_audit(e+1)` from `K_master`. Members invited before
the rotation retain access to their assigned epochs only. Members invited after rotation
receive only the new epoch keys.

`SK_mod` is not epoch-scoped in the current implementation. The same moderation keypair
is used across epochs and is labelled `SK_mod(e)` in the protocol to reserve for future
per-epoch rotation.

## Key loss scenarios

See [RECOVERY_RUNBOOK.md](RECOVERY_RUNBOOK.md) for step-by-step recovery procedures.

| Scenario | Recoverable? | How |
|---|---|---|
| Leader loses device, has recovery phrase | Full | `wevibe_recover_org` with phrase → re-derive epoch keys; re-import sealed envelopes generated by anchor |
| Leader loses device, no phrase | Partial | `SK_mod` recoverable from personal envelope; `K_master` is gone — derive new org or migrate |
| Moderator loses device | Full | Leader re-invites moderator with a new invitation |
| Member loses device | Full | Leader re-invites member with a new invitation |
| Leader loses local mod key only (identity intact) | Automatic | Re-import personal envelope; anchor will rehydrate `SK_mod` |
